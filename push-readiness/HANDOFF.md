## Narrow Fixes

- Prepare now uses existing Auth SHARE -> profile NO KEY UPDATE -> installation/budget order. Captured subject/session and canonical Home admission are rechecked after waits, including existing-slot replay and INSERT triggers. Same-account profile locking serializes both cap and budget; cross-account install-ID conflicts roll back the losing budget charge.
- Existing indexed rows enforce the 16 active-slot cap (unbound preparations included). One RLS/private `push_creation_budget` row per Auth user stores only window start/count and cascades on Auth user deletion. A separate fixed budget is necessary because accepted anonymous cleanup intentionally clears installation `user_id`; counting remaining live rows alone permits unlimited create/revoke churn. No caller-selected key, settings UI, generic quota RPC or external limiter added. Twenty means a fixed account-local hour, not a sliding-window/global fair-use guarantee.
- `register_push_token` retains account/capability/environment/platform binding, unique environment/token behavior and RPC shape. Its post-update check now requires canonical Home as the precheck does, so a late terms change cannot commit a token. Stored tokens still never authorize sending.
- Nullable private `cleanup_session_id` retains the latest validated session linkage when cleanup clears operational user/session/token fields. Register moves the anchor on a valid session refresh. Capability cleanup fills it opportunistically for a known legacy row, preserving historical rows during migration. Existing Auth session deletion cascades retired slots; no new Auth mutation, cleanup job, time-based deletion, backfill or purge is introduced. Supporting user/state and session indexes avoid global scans for normal scoped operations.
- Repeated terminal revocation performs no row/timestamp rewrite. Unknown/wrong capabilities still cannot create rows. Lifecycle-revoked rows can still clear retained operational identity with their capability; revoked slots are never reopened by prepare/register.

**Rate is not retention:** 20 creations/hour bounds successful row creation rate, not permanent table size. Session rows may persist indefinitely; this batch does not verify hosted session deletion or promise eventual tombstone deletion. Existing already-retired rows with no session anchor are deliberately unchanged. No tombstone TTL is invented because deleting one while its session remains usable could allow delayed preparation to recreate it. Sender freshness/invalid-token handling and retention decisions remain separate. On legacy installations above16, existing replay/refresh/cleanup works but no new slot is admitted until below cap; no existing row is removed.

Safe client errors are `PT429 push_capacity_reached` / `PT429 push_creation_limited`, containing no token, capability or account details. `lib/services/firebase/firebase_service.dart::_registerPush` already catches registration failure, disables optional push, attempts capability cleanup and shows generic `Push registration unavailable. Retry after connecting.`; no automatic registration retry. `push_token_store.dart` persists pending capability before prepare and does not silently rotate until revocation succeeds. No client change is required for safe failure, though the existing message does not distinguish quota from connectivity. Recovery/onboarding ordinary access is unchanged: push already requires Home/terms, unlike availability/support.
